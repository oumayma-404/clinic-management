# ClinicManagement.Domain

> The innermost Clean Architecture layer: pure C# domain model (entities, aggregates, value objects, enums, a couple of pure domain services) plus repository **interfaces**. No EF Core, no ASP.NET, no infrastructure dependencies. The `.csproj` has **zero package/project references** — the dead domain-events pipeline (its only reason for a `MediatR.Contracts` ref) was removed in `french-localization-and-cleanup`.

## Base classes & patterns (`Common/`)

- **`Entity<TId>`** (`Common/Entity.cs`) — carries **`uint Version`**, the optimistic-concurrency token EF maps
  onto PostgreSQL's `xmin` (private setter: EF owns it, the domain must never assign it). Identity-based equality (`==`/`!=`/`Equals`/`GetHashCode` by `Id`, with a runtime-type check). `Id` has a `protected set`. Generic over the id type (most use `Guid`; `User` uses `string`).
- **`AggregateRoot<TId> : Entity<TId>`** (`Common/AggregateRoot.cs`) — a bare marker base for aggregate roots (the transactional consistency boundary). Carries **no** domain-events list (the dead pipeline was removed).
- **`ValueObject`** (`Common/ValueObject.cs`) — structural equality via abstract `GetEqualityComponents()` (subclasses `yield return` their components).
- **`FdiTooth`** (`Common/FdiTooth.cs`) — static FDI tooth-number validator (`IsValid`/`IsAdult`; adult 11–48, child 51–85). Shared by `DentalRecordAct`, `TreatmentPlanItem`, and `ToothState`.

### Conventions every domain type follows
- Private parameterless ctor `private X() { }` **for EF Core**; a public ctor (or static factory) that sets `Id` and `CreatedAt = DateTime.UtcNow`.
- All setters are `private set;` — state changes only through intention-revealing methods (`Issue()`, `RecordPayment()`, `AddStock()`, `Confirm()`…).
- Invariants enforced in ctors/methods via `ArgumentNullException` / `ArgumentException` / `InvalidOperationException` (newer entities throw **French** messages).
- `CreatedAt` / nullable `UpdatedAt` are pervasive; `UpdatedAt` is bumped on mutation (often via a private `Touch()`).
- Child collections are `private readonly List<>` exposed as `IReadOnlyCollection<>`.
- **Money is TND millimes** (`decimal`, 3 decimals, away-from-zero). `InvoiceCalculator` is the single arithmetic authority; billing entities round through it.

## Aggregate Roots (`AggregateRoot<...>`)

**Core / scheduling**
| Aggregate | File | Key responsibilities |
|-----------|------|----------------------|
| `Patient` | `Entities/Patient.cs` | Central aggregate. VOs: `Email`, `PhoneNumber`, optional `Address`, `InsuranceInfo`, `CnamInfo` (CNAM identity). Owns `Flags`, `Files`, `Appointments`, `MedicalHistoryEntries`, `FamilyHistoryEntries`. Recall/relance fields (`RecallSnoozedUntil`/`RecallReason`/`LastRecallContactedAt`) + emergency-contact fields. **`ReferredBy`** (« adressé par ») and **`Notes`/`ImportantNotes`** are free text, deliberately: the referrer is normally a practitioner *outside* the clinic so an FK to `Doctor` could not record the ordinary case, and the notes are read as a paragraph — never filtered, sorted or counted — so a child table would buy only a second write path. `ImportantNotes` is a separate column rather than a convention inside one blob because it is rendered highlighted at the top of the patient's file. Distinct from `DentalRecord.Notes`/`ImportantNotes`, which describe **one séance**. Belongs to a `Clinic`. |
| `Appointment` | `Entities/Appointment.cs` | **A declared transition table** (`AllowedTransitions` + `NextStatusesFrom`/`CanTransition`/`FrenchLabel`) is the single authority; every mutator funnels through one guard that throws a French message naming **both** statuses. Notable edges: `Completed → Cancelled` is the **only** exit from `Completed` (a visit is auto-completed by saving its fiche, so a mis-saved one used to be permanent); `Confirmed → Scheduled` is deliberately absent (`Reschedule` *preserves* `Confirmed`/`InProgress` — the A-2 fix — so it never attempts it); `NoShow → Cancelled` is kept because `CancelRecurringSeriesCommand` voids missed occurrences. `MarkVisitCompleted` returns a **`VisitCompletionOutcome`** (`Completed`/`AlreadyCompleted`/**`Contradicted`**) rather than `void`, and never throws — both callers are post-commit best-effort helpers where a throw would skip `CancelPostVisitReviewAsync` and leave the post-visit prompt nagging forever. `BookedOutsideWorkingHours` records a confirmed out-of-hours exception. State machine over `AppointmentStatus` (`Confirm/Start/Complete/MarkVisitCompleted/Cancel/MarkAsNoShow/Reschedule/Reactivate`). Optional `PatientId`; `DoctorId` is a **FK to `Doctor`** (nav property); `RecurringAppointmentId`; `GoogleCalendarEventId` for sync. **Owns `Procedures` (`AppointmentProcedure`) — a séance is several acts** — and `ProcedureTypeId`/`ProcedureDurationMinutes`/`ProcedureColorHex`/`TreatmentPlanItemId` are a **derived snapshot of the first row**, re-derived by `SetProcedures` (replace-semantics; refuses a duplicate act or a duplicate plan step). ⚠️ `SetProcedureType` now means "exactly this one act" and *replaces* the list (it preserves the plan link, which is `SetTreatmentPlanItem`'s business); use **`RefreshProcedureSnapshot`** to re-snapshot a renamed procedure without deleting the other acts. Reads that ask "which devis steps does this visit carry out?" must use **`LinkedTreatmentPlanItemIds`** (child links + the legacy scalar), never the scalar alone; `TotalProcedureDurationMinutes` is the séance's summed length. |
| `Clinic` | `Entities/Clinic.cs` | Tenant root. `Name`, `City`, contact info, unique join `Code`, `LogoUrl`. **Billing settings** (`MatriculeFiscal`, `VatApplicable`/`VatRate`, `StampDutyEnabled`/`StampDutyAmount`) frozen onto each invoice at issue. Per-clinic **Google Calendar** (`GoogleRefreshToken`/`GoogleCalendarId`). `WorkingHoursJson` (opaque). `RecallIntervalMonths`. Owns `Users`/`Patients`/`Appointments`. |
| `Doctor` | `Entities/Doctor.cs` | Practitioner profile in a clinic. `LinkToUser(userId)` ties it to a `User`. `FullName` computed. CNAM/official-doc fields: `CodeProfessionnelSante`, `OrdreNumberCnomdt` (CNOMDT), cachet blob (`CachetStorageKey`/`CachetContentType`). Optional per-dentist `WorkingHoursJson`. |
| `User` | `Entities/User.cs` | **`AggregateRoot<string>`** — Id is the Auth0 `sub` (Cloud) or `local\|{guid}` (Local). `Role` string + `IsDoctor/IsSecretary/IsAdmin`. The closed set is now **declared** here — `RoleAdmin`/`RoleDoctor`/`RoleSecretary` + `AssignableRoles` + `NormalizeRole(value)` (canonical spelling or null) — where it used to be only a comment plus literals scattered across the policies and the two self-registration commands. **`ChangeRole(role)`** validates against it, bumps `TokenVersion` (the JWT carries the role, so the old one would otherwise stay live for the token's lifetime) and returns `false` on a no-op. It **replaced** `Update(string role, string? email = null, string? fullName = null)`, which had no caller and was a trap: the natural one-argument call assigned the two defaulted nulls and wiped the user's email and full name. Belongs to a `Clinic`. **Local-auth:** nullable `PasswordHash`, `IsActive`, `MustChangePassword`, `LastLoginAt`, lockout state (`FailedLoginAttempts`/`LockoutEnd`, 15-min `LockoutDuration`). Factories `CreateLocalUser(...)` and — since I5 — **`CreateSelfRegistered(...)`**, which is byte-identical except that the account is created **inactive**: `POST /api/auth/register` used to mint a *live* account behind nothing but a **6-character** clinic code shown on a settings screen and known to everyone who ever worked at the practice, so learning it was enough to read every patient record. A separate named factory rather than an `isActive: false` argument, because the only other caller is first-run `setup` — whose admin must log in immediately, or the clinic is locked out of itself before it has anyone to approve them. **`IsPendingActivation`** (`!IsActive && LastLoginAt == null`) distinguishes « never let in » from « switched off after use »; derived, so I5 needed no column. `SetPassword`/`UpgradePasswordHash`, `RecordSuccessful/FailedLogin`, `Activate`/`Deactivate`, `PromoteToAdmin`. Cloud users leave `PasswordHash` null. |
| `PlatformAccount` | `Entities/PlatformAccount.cs` | **The vendor's console identity** (`platform-console` FR-1) — a population separate from `User`, with its own credentials, lockout, sessions and a mandatory TOTP second factor. ⚠️ **No `ClinicId`, so it is outside the EF tenant filter by construction** — the same position `ClinicSignup` is in, and for the same reason: a row that exists precisely because it belongs to no cabinet cannot be filtered by one, and the guard that derives the clinic-owned set from that column never sees it. A second entity rather than a role on `User` because `User.ClinicId` is non-nullable and is what every tenant check reads: expressing this as a clinic role would mean a sentinel clinic (the defect class four contact sentinels were retired for) or re-auditing every read that assumes the column. `ProtectedTotpSecret` arrives **already encrypted** (Domain references nothing; `PlatformSecretProtector` does the work) and `TotpEnrolledAt` being null with a secret present is the « issued, not yet confirmed » state a password-only sign-in must refuse carrying nothing (EC-2). Lockout mirrors `User`'s 50-attempt cross-source backstop deliberately — two copies rather than a shared base, because the numbers are a policy decision per population. |
| `PlatformRecoveryCode` | `Entities/PlatformRecoveryCode.cs` | One single-use recovery code (child of `PlatformAccount`). Stored as a **plain SHA-256**, and that is reasoned rather than lax: iterated hashing exists for low-entropy human-chosen secrets, while this is 20 characters of CSPRNG over a 32-symbol alphabet — 100 bits, nothing to brute-force — and the comparison has to be **deterministic** because the aggregate itself checks a presented code, which a per-row salt would turn into a password hasher inside Domain. **Consumed, never deleted**: a spent code and a code that never existed are the same refusal to a caller and different facts to whoever reads the account afterwards. |
| `PlatformAccessEntry` | `Entities/PlatformAccessEntry.cs` | ⚠️ **Part 4 adds `SubscriptionPeriodId` and a partial-unique `IdempotencyKey`** — the ledger is also where « a double-click produces one entry » (AC-4.6) is *enforced*, by the index rather than by a handler reading first, which two simultaneous submissions both pass. It lives here rather than in a table of its own because every console write already produces exactly one row here, in the same transaction as the write; the row also names the entry it created, so a replay returns the **first** outcome instead of guessing at it. Neither column is a foreign key, for the reason the whole type has none. **The console's own append-only ledger** (`platform-console` Part 3, FR-5): which console account did what, to which cabinet, when. ⚠️ **Not `AuditEntry`, and the difference is the direction.** That ledger answers « who at this cabinet changed this record? » and is read by the cabinet's own admin; this answers « what did the *vendor* do, and to whom? », its actor belongs to no cabinet, and its most important row — a detail being merely **read** — is not a mutation at all, so nothing in a save-interceptor could ever see it. ⚠️ **No FK to `Clinics` and none to `PlatformAccounts`**, unlike its cascading Part-2 siblings: a cascade would erase the record that somebody looked at a practice that has since been closed, which is the first row an audit of this console would want. `ClinicName` and `AccountEmail` are therefore denormalised so such a row still names both parties. ⚠️ **Append-only by construction**: no mutator on the type, no update or delete on its repository, no write endpoint — `AuditController`'s shape, and for its reason. |
| `ClinicSubscription` | `Entities/ClinicSubscription.cs` | **A cabinet's dated right to record new work** (`clinic-subscription` FR-1). One row per clinic; `EndsOn` is an **inclusive clinic-local day** and a denormalised full re-fold of the `SubscriptionPeriod` ledger, so the gate reads one indexed row instead of a ledger. ⚠️ **`RecomputeFrom(wholeLedger, whenUtc)` is the only writer of `EndsOn`, the trial's included** — and it takes the instant like every other mutator on the class rather than reading the clock, so a test can control it — three ways it drifts are designed out: an incremental `EndsOn += duration` makes cancelling any but the latest entry change no date (AC-5.4); a fold taking « today » moves unrelated dates on every recomputation; and a *second* date-computing site (a hand-written trial end) disagrees with its own fold by one day and makes `verify-schema`'s `subscription-end-date-matches-ledger` red on every new cabinet. `SetPlan` records AC-5.1's optional forfait and touches no date (a label and a price; it gates nothing). `Suspend`/`Unsuspend` carry a mandatory reason, and suspension **outranks** expiry (EC-11 — a suspended cabinet reads « Suspendu », never « Expiré », because a payment will not fix it). `SubscriptionState` is **derived, never stored**: a stored copy would be a fourth thing able to disagree, and it would have to change at midnight with no write to change it. ⚠️ **`LatestCoverKind` (`platform-console` Part 4) is the one thing besides `EndsOn` that `RecomputeFrom` writes**, from the *same* fold — the kind of the last non-cancelled entry, so the vendor console can filter « en essai » as a SQL predicate before a page is cut (AC-2.4a) instead of folding N cabinets' ledgers. It is deliberately **not** « what covers today »: that is a function of the ledger *and of today*, so a stored answer would be correct only until the next midnight and would need a daily pass — reintroducing exactly the staleness the clock-free fold is designed to avoid. `verify-schema`'s `subscription-cover-kind-matches-ledger` re-derives it. |
| `SubscriptionPeriod` | `Entities/SubscriptionPeriod.cs` | One entry of the append-only ledger: a stretch of time and where the entitlement came from. **Append-only** — no mutator for the duration, amount or kind; a mistake is `Cancel`led with a written reason, stays visible struck through, and the date recomputes, possibly into the past (AC-5.5, EC-4). ⚠️ **`ExplicitEndsOn` is validated, unlike every other named end date in this product**: refused before its own `RecordedOnClinicDay` and beyond `MaxExplicitEndYears` (5) after it — a mistyped year is the one input here that can make a paying cabinet read-only mid-consultation or grant cover for ever. ⚠️ **Exactly one duration form, or none**: `DurationMonths` / `DurationDays` / `ExplicitEndsOn` are mutually exclusive and all three absent means open-ended — two set is not a longer period, it is a row the fold would have to guess at. `RecordedOnClinicDay` is the fold's anchor and the reason the fold needs no clock. ⚠️ **An `AggregateRoot` on purpose**: `AuditSaveChangesInterceptor` writes one row per mutated *root*, so as a plain entity a grant and a cancellation would produce no audit row and FR-12 would be silently false — the same reason `ClinicSubscription` is one. |
| `MessagingAllowanceEntry` | `Entities/MessagingAllowanceEntry.cs` | **One allocation of WhatsApp reminder capacity** (`vendor-whatsapp-messaging-quota` FR-2): a figure, the Tunisian month it takes effect in, and what the vendor was paid. **Append-only** — no mutator for the figure, the month, the amount or the kind; a mistake is `Cancel`led with a written motif, stays visible struck through, and every month it fed recomputes. ⚠️ An `AggregateRoot` **on purpose**, and the opposite decision from `ClinicMessagingMonth` beside it: `AuditSaveChangesInterceptor` writes one row per mutated *root*, so as a plain entity a grant and a cancellation would produce no audit row at all — the **entry** is the audited artefact, the month row is a counter written minutely. ⚠️ `EffectiveMonth` is an `AAAA-MM` **string** end to end, zero-padded, so lexicographic order *is* chronological order and « effective month ≤ M » needs no conversion in SQL, in the fold, or in a console argument. ⚠️ `Messages` of **zero is legal and meaningful** for a standing entry (« this cabinet sends no WhatsApp reminders ») and is not the same state as having no entry at all; a **top-up** of zero is refused, because it would be indistinguishable on screen from one the vendor meant to make. `Amount` is **null** for a complimentary allocation rather than `0`, which would read as a transaction that happened for nothing — and it is never the clinic's money (FR-2) |
| `AuditEntry` | `Entities/AuditEntry.cs` | **The audit ledger** (`adoption-qa-i-access-control-and-audit` I6) — one row per mutated aggregate: actor (`UserId` + denormalised `UserEmail`), `ClinicId?`, `EntityType`, `EntityId`, `AuditAction`, a compact `ChangedFields?` summary, `OccurredAt`. Written **only** by `AuditSaveChangesInterceptor`; there is no command, no mutator and no write endpoint — a ledger somebody can correct is not evidence. ⚠️ Three deliberate shapes: **`ClinicId` is nullable** (a job or console verb can mutate a row with no clinic derivable from it, and `Guid.Empty` would be a sentinel reading as a real clinic in the `(ClinicId, OccurredAt)` index — the defect class the four contact sentinels were retired for); **`EntityId` is text** because `User` is keyed by a string while everything else is a `Guid`; and it holds **no FK** to `Clinics` or `Users`, since its most valuable rows are the ones about a deleted account. It is deliberately *not* `CreatedBy`/`ModifiedBy` on `Entity<TId>`: that would be a write-path obligation on 38 entities, any writer that forgets it produces an unattributed row indistinguishable from a legitimate one, and it answers nothing about a delete — which is the question most often asked. An interceptor cannot be forgotten. |
| `ProcedureType` | `Entities/ProcedureType.cs` | Priced procedure catalog: `Name`, `DefaultDurationMinutes` (1–479), `DefaultCost`, `Color` (`ColorHex` VO), optional **`Category`** (clinical discipline — open text canonicalised through `Services/ProcedureTypeCategories` on **every** write, ctor included; null = unfiled), optional `ResultingCondition` (odontogram state a matching act produces), active flag. ⚠️ `Category` is what `Description` used to hold: `ProcedureTypeCatalogSeed` had no column for a discipline and passed it positionally into the ctor's `description` slot, so every seeded clinic carried « Endodontie » in a field the form labels « Description (optionnel) » — and the act picker grouped on it while documenting that it must not be trusted. `AddProcedureTypeCategory` moves those values and **clears the description it took them from**. The two parameters are still adjacent nullable strings, so the seed and `CreateProcedureTypeCommand` both pass **named** arguments deliberately. `IsUsedByFutureAppointments(...)` guards deletion. Owns a **material list** (`ProcedureTypeMaterial`, AC-P4.9): what performing the act consumes from stock. `SetMaterials` replaces the list wholesale and refuses a duplicate item. **Opt-in** - an empty list consumes nothing, which is the majority case. It hangs off `ProcedureType` and *not* `DentalActCode` because `DentalRecordAct` has no `DentalActCodeId`, so a list there could never be consumed on fiche save (DEV-4). |
| `Supplier` | `Entities/Supplier.cs` | **Any outside contact the cabinet orders from or sends work to** (`stock-fournisseurs`): a laboratoire de prothèse, a laboratoire d'analyses, a dépôt dentaire, a maintenance technician. It replaced the free-text `StockItem.Supplier` **and** stands beside `LabWorkOrder.Prosthetist` — two columns that named somebody nobody could call, which is why « Stock faible » and a bon en retard could not answer « qui est-ce que j'appelle ? ». ⚠️ **`PhoneNumber` is a plain string, not the VO**: a number that is not a deliverable Tunisian one is *stored* (EC-1), because a dépôt with a French number is a real supplier — what it loses is the WhatsApp action, which the read side derives and the screen explains. ⚠️ **`Address` is one free-text line and deliberately not the `Address` VO**, which requires street/city/state/zip and so could not represent « Zone industrielle, Ben Arous » or the ordinary empty case. ⚠️ **Deactivating hides it from the pickers and erases nothing**: an article or a bon already naming it keeps rendering the name and keeps its WhatsApp action, and `ISupplierRepository.GetByIdsAsync` ignores `IsActive` for exactly that reason. Deleting one that is referenced is refused in the handler with the counts named per table; the FK is `Restrict` as a backstop only |
| `StockItem` | `Entities/StockItem.cs` | Inventory item, now **per-lot**. Owns `StockBatch` children (AC-P4.1) - `ExpiryDate`/`BatchNumber` used to be two scalar columns that `AddStock` **overwrote**, so a second delivery destroyed the first lot's date. `AddStock` creates a lot; `AttachExistingBatch` adds one already counted in `CurrentStock` (the migration's opening batch, so it must not increment). **`ConsumeStock` draws down FEFO** - soonest expiry first, undated lots last - and **returns the shortfall rather than throwing**: recording a visit is never blocked by a stock discrepancy, so on-hand may go negative (AC-P4.12). `RemoveStock` keeps the throwing contract for an explicit manual sortie. `SetCurrentStock` returns the **signed delta** so the caller can write the `StockMovement` AC-P4.15 requires - it returned void, which is why its only caller wrote none and the ledger stopped reconciling. `EarliestRelevantExpiry`/`HasExpiredStock`/`HasStockExpiringSoon`. |

## Domain services (`Services/`)

- **`InvoiceCalculator`** (`Services/InvoiceCalculator.cs`) — pure, testable Tunisian money arithmetic (no persistence). `RoundMoney` (millime, away-from-zero), `LineTotal`, and `Compute(totalHt, vatApplicable, vatRate, stampDutyAmount) → InvoiceTotals(HT, VAT, TTC)`. The single rounding authority reused by `Invoice`, `TreatmentPlan`, `Installment`, `DentalRecord`, and their lines.
- **`SubscriptionLedger`** (`Services/SubscriptionLedger.cs`) — folds a cabinet's append-only ledger into the one
  date the product enforces on. Pure, total, and **clock-free**. `FoldWithSpans` is the implementation and `Fold` a
  call onto it, so the write path, `verify-schema` and the history screen cannot hold three arithmetics; the spans
  are FR-2's *derived* « période couverte » (a cancelled entry gets `(null, null)`, an open-ended one
  `(FromDay, null)`). Since `platform-console` Part 4 it returns a named **`SubscriptionFold`** carrying a third
  answer, **`LatestCoverKind`** — the `Kind` of the last non-cancelled entry in fold order, null for a wholly
  cancelled ledger. It is folded here rather than derived beside `RecomputeFrom` so the ordering
  (`RecordedAtUtc` then `Id`) exists exactly once; see `ClinicSubscription.LatestCoverKind` for why it is storable
  and « what covers today » is not.
  ⚠️ **No clock parameter, and that is load-bearing.** The naive reading of AC-5.2 (« the later of the current end
  or today, plus the duration ») is to pass `today` in — then the result depends on *when* it is recomputed: a lapsed
  entry restarts from today on every re-fold, cancelling one entry moves unrelated dates, and
  `subscription-end-date-matches-ledger` flaps daily. Each entry anchors on its **own** recorded clinic-day instead,
  which reproduces AC-5.2 exactly, because at the moment an entry is recorded its recorded day *is* today.
  ⚠️ **The cursor is exclusive — « the first day not yet covered » — and that is what makes one formula correct for
  both anchors.** A recorded day is an inclusive *start* (creation day is day 1) while a running end is an inclusive
  *end*, so a single `anchor + duration` over both is wrong in one of the two cases whichever way it is written: it
  yields a **31-day** trial (AC-1.1 says 10 Aug → 8 Sep) or a one-day grant on a lapsed cabinet (EC-3 says end
  20 Sep + 12 months → 20 Sep 2027, with no −1). ⚠️ **The month branch advances from the day BEFORE the start** (`start.AddDays(-1).AddMonths(n).AddDays(1)`), because the clamp belongs on the *inclusive* end: 31 Jan + 1 month **ends 28/29 Feb** (FR-2, EC-3), where advancing the exclusive cursor with `AddMonths` lands a day short whenever the anchor's day outruns the target month — silently, unpredictably, and in the vendor's favour. ⚠️ **An `ExplicitEndsOn` entry can only ever extend cover** (`Later(explicit + 1, start)`): a recorded entry must never reduce a date, or a mistyped `--until` revokes months somebody paid for with no refusal and a success message. Shortening is a cancellation's business alone (AC-5.2).
  It takes a `SubscriptionLedgerEntry` record rather than the entity so there is exactly one fold: the write path
  projects through `SubscriptionPeriod.ToLedgerEntry()`, and `verify-schema` — which reads over raw ADO and builds
  no entities — projects the same shape out of PostgreSQL.
- **`MessagingAllowanceLedger`** (`Services/MessagingAllowanceLedger.cs`) — folds a cabinet's append-only WhatsApp
  allocation ledger into the one figure a month is metered against. **Pure, total and clock-free.** The standing
  figure is the *last* non-cancelled `Standing` entry effective on or before the month; every non-cancelled `TopUp`
  effective *in* that month is added on top.
  ⚠️ **The month is a parameter and there is no clock**, exactly as in `SubscriptionLedger`: the naive « what is
  this cabinet allowed *now* » makes the answer depend on when it is recomputed, so a re-fold after midnight on the
  1st would silently rewrite a **closed** month's snapshot and `verify-schema`'s `monthly-allowance-matches-ledger`
  would flap monthly. It is also what lets `messaging-report --month 2026-07` answer for a month that has closed,
  which is when the vendor reconciles — and it is free, because the fold never needed a clock.
  ⚠️ **No entry folds to `null`, never to `0`** — opposite facts (see `ClinicMessagingMonth`), and collapsing them
  would tell a practice « votre forfait est épuisé » about a row nobody ever wrote.
  ⚠️ **A cancelled entry contributes to no month it fed, the current one included**, while a *lowering* waits for
  the next — the deliberate asymmetry between AC-7.4 and AC-6.4, and it falls out of the fold for free.
  ⚠️ It **orders the entries itself** rather than trusting the caller: the answer depends on the order, and two
  call sites (the repository read and `verify-schema`'s raw ADO projection) would otherwise each carry an `ORDER BY`
  the fold silently depends on. Like `SubscriptionLedger` it takes a `MessagingAllowanceLedgerEntry` **record**
  rather than the entity, so there is exactly one fold for the write path, the reads and the schema gate.
- **`CategoryFolding`** (`Services/CategoryFolding.cs`) — the accent-, case-, space- and punctuation-insensitive
  comparison key every **open category set** folds on, plus the shared `NormalizeAgainst`/`IsCanonicalIn` bodies.
  There are three such sets now (`ProcedureTypeCategories`, `SupplierCategories`, `StockCategories`) and three
  private copies of the fold is the shape this repo keeps finding: they agree today, and the first to gain a rule
  the others do not is the one that silently shards a category. `ProcedureTypeCategories.Fold` delegates here.
- **`SupplierCategories`** (`Services/SupplierCategories.cs`) — what an external contact *is* to the cabinet.
  Deliberately spans **laboratories and goods** (« Laboratoire de prothèse », « Analyses / Anatomopathologie »,
  « Consommables », « Maintenance et services »), because a fournisseur here is any outside party the practice
  deals with rather than a stockroom supplier alone — which is why both `StockItem` and `LabWorkOrder` point at
  the one aggregate. Open with suggestions, same shape and same `Normalize` obligation as the acts' disciplines.
- **`StockCategories`** (`Services/StockCategories.cs`) — a stock article's category, and the retirement of the six
  English storage keys the product shipped with. ⚠️ They were a *closed* set mapped to French at display time, this
  repo's standing convention — but the set had stopped being closed (`GET /api/stock` already served the clinic's
  own categories as a filter facet, and nothing refused one typed straight into the database), so a clinic-authored
  category rendered raw beside six translated ones. The storage key is the French label now and the migration
  rewrote the six. ⚠️ **`LegacyKeys` is the single authority for that rewrite** *and* keeps folding at runtime: an
  older client, a bookmarked `?category=PPE` and a CSV import can all still present one.
- **`ProcedureTypeCategories`** (`Services/ProcedureTypeCategories.cs`) — the act catalogue's clinical disciplines:
  `Canonical` (twelve French labels in **clinical order**, mirroring `ProcedureTypeCatalogSeed`'s row order, not the
  alphabet), `IsCanonical`, and `Normalize`. The set is deliberately **open** — a practice may file work under
  « Occlusodontie » and it is kept verbatim — so `Canonical` is a *suggestion* list, not a constraint.
  ⚠️ **`Normalize` is what makes an open set survivable, and every write path must go through it** (the entity's
  ctor and `UpdateCategory` both do). The entire value of a category is that acts sharing one group together, and
  « endodontie » / « ENDODONTIE » / « Endodontie » are three groups to PostgreSQL and one to a dentist — so an
  admin who types instead of picking would silently shard a discipline. The fold ignores case, accents **and
  punctuation**, the last specifically for « Chirurgie/Extraction », written with and without spaces around the
  slash about equally often. A label that folds onto nothing passes through untouched.
- **`PaymentDateRules`** (`Application/Features/Invoices/PaymentDateRules.cs`) — the shared guard for every
  caller-supplied money date (`PaidOn`, an installment payment's, an avoir's `RefundedOn`). These reach the
  domain as non-nullable `DateTime`s, so a client omitting the key posts `0001-01-01`: the row still moves the
  collected total but is invisible in every cash window forever. A future date is the mirror image.
- **`PlanBillingRules`** (`Services/PlanBillingRules.cs`) — pure policy: **which treatment plans carry patient debt**, shared by all four money reads (« Solde patient », « Créances », la caisse, dashboard) so they can never report different figures. `DebtBearingPlanStatuses`/`CarriesDebt` (Accepted/InProgress/Completed only — a `Draft` devis is an unaccepted quote, a `Cancelled` one is void), `RepresentsItsPlan(InvoiceStatus)` (non-Draft, non-Cancelled), and two `BilledPlanIds` overloads (from loaded `Invoice`s, or from the light bridge-link tuple projection) that yield the plans a devis→facture invoice already represents. ⚠️ Since `data-and-money-integrity` these rules apply to **outstanding balances AND collected cash**. That is a
deliberate reversal of the previous note: the devis→facture bridge now carries the plan's collected payments onto
the invoice at issue, so the receipts live on the invoice track and counting the plan too would double them. The
exclusion is read-side only and self-correcting — a `Draft` bridge does not exclude, and cancelling it hands the
plan straight back to both reads.

## Domain Events — removed

The `Events/` folder, `IDomainEvent`, and `AggregateRoot`'s event list were removed (`french-localization-and-cleanup`): a dead "parallel-universe" pipeline (`SaveChangesAsync` never drained events; zero handlers). Side effects (in-app `StaffNotification`s, SMS/WhatsApp reminders) are produced **inline, post-commit** from the command handlers via `INotificationGenerator`/`IReminderScheduler`.

## Gotchas
- `User` is keyed by **string** — the Auth0 `sub` (Cloud) or `local\|{guid}` (Local) — unlike all other `Guid`-keyed types.
- `Appointment.PatientId` and `DoctorId` are optional: an appointment can be a "blocked"/occupied slot with no patient. `DoctorId` is a real FK to `Doctor` (not free-text). In-app notifications are only generated for patient-bearing events and never for the actor.
- **Denormalized snapshots are intentional, not FKs**: `Appointment` snapshots procedure duration/color; `DentalRecord` derives its summary/cost/teeth from its acts; `InvoiceLine`/`TreatmentPlanItem` snapshot `CodeActe`; `MedicalDocument` snapshots patient/clinic/doctor.
- **CNAM/DCH/medication catalogs are per-clinic** (each has `ClinicId` and a `HasQueryFilter`; every clinic is seeded the same default set, then edits stay private). ⚠️ Their in-source class/interface docstrings still say "global reference data (no ClinicId)" — that wording is stale; trust the `ClinicId` property + query filter.
- Money everywhere is TND **millimes** (3 decimals). Round only through `InvoiceCalculator`.
- **`ColorHex`'s curated palette has no frontend counterpart to keep in sync any more** — the browser had a hardcoded hex array, then just the French *names*, and now neither: `GET /api/procedure-types/colors` serves the families **and their labels**, so this file is the sole authority on which colours exist and on what they are called. Grouped rather than flat because an act catalogue outgrows ten colours long before it outgrows twelve hues, and the picker offers a hue first and its nuance second.
- `ClinicReminderSettings` and `NotificationRead` are the two non-standard keys: the former's `Id` **is** the clinic id (1:1 shared PK); the latter is a plain composite-key class, not an `Entity`.
