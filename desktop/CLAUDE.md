# ClinicManagement.DesktopShell

Thin **WPF + WebView2** client shell for the Local/offline-LAN deployment (Phase 5, FR-F). A staff PC runs this instead of a browser: it points a WebView2 control at the clinic server's HTTPS front door and renders the same Next.js web app. **Windows-only** (`net8.0-windows`), a **standalone solution** (`ClinicManagement.DesktopShell.sln`) — deliberately NOT part of `api/ClinicManagement.sln` (different SDK/target; keeps the backend build gate clean). Built/published only via `packaging/publish-server.ps1`.

## What it does
- Connects **only** to the Kestrel **HTTPS front door** (`https://<host>:<port>`, default port 5001) — never the internal Next web port. The server terminates TLS once and proxies pages itself, so the shell is a pure viewer.
- Stores the server address once per user and reuses it on every launch; changeable later without reinstalling.
- Shows friendly, recoverable French screens (configure / connecting / unreachable) instead of blank pages or raw browser errors.

## Files
| File | Role |
|------|------|
| `MainWindow.xaml` / `.cs` | The single window. **Five** mutually-exclusive view states — `WebView` / `Connecting` / `ServerConfig` / `Unreachable` / **`UpdateRequired`** — toggled by visibility, plus a dismissible **update-notice strip** docked above them. ⚠️ The strip is *docked*, never drawn over the WebView, so it can never cover a patient record; the wall (`UpdateRequired`) replaces the app entirely, because below the floor every `/api` call returns 426 and the loaded page would be a screen where nothing works. A dismissal is remembered **per version** (in memory only) so hiding today's notice cannot suppress the next release's. ⚠️ **There is no menu bar, and its absence is the design** — see `WindowTheme.cs`; **Changer de serveur…** and **Recharger** are prepended to the WebView's own right-click menu (`ContextMenuRequested`), and the unreachable screen keeps the button it always had, which is the case that matters. Initializes the WebView2 core against a **per-user** user-data folder (`%LocalAppData%\ClinicManagement\WebView2`) so a `%ProgramFiles%` install works without elevation. Uses `Navigate()` (not `Source=`) so Retry/Reload re-attempt. A failed `NavigationCompleted` → the unreachable screen. |
| `ServerConfig.cs` | `ServerConfig` (Host/Port → `BaseUrl`, HTTPS only) + `ServerConfigStore` persisting to `%AppData%\ClinicManagement\server.json` (corrupt/missing → first-run prompt). `ParseAddress` accepts a bare host, `host:port`, or a full URL. ⚠️ A **missing port is left unresolved**, not defaulted to 5001 — see `ServerProbe.cs`. |
| `ServerProbe.cs` | Settles an address that named no port, by trying `CandidatePorts` (**443 then 5001**) and taking the first that answers; the result is persisted as explicit so it costs one round trip per address. A TLS failure counts as « answered » — a self-signed LAN certificate is the expected case. **The rule is shared with both mobile shells** and is stated once in `mobile/CLAUDE.md` § « The port rule »; do not change it in one client alone. |
| `ClientRequirements.cs` | The launch-time read of `GET /api/meta/client-requirements` — the desktop twin of the mobile shells' probe. Reports the assembly's own `<Version>` as `X-Client-Version`, compares it against the server's floor and current release, and exposes `StoreUrls.Windows` as the download link. ⚠️ **Unreadable means « no floor », never « refuse »** — offline, an older server without the route, malformed JSON and an unset floor all pass. |
| `WindowTheme.cs` | **The chrome follows the web app, not Windows.** The shell used to be a light title bar and a light WPF `Menu` strip stacked above an app the user had put in dark mode — three bands, two of them a different product. The menu is gone, and the caption/text/border are tinted through `DwmSetWindowAttribute` to the app's own `--background`/`--foreground`/`--border`, converted from oklch once. ⚠️ The theme is read from the page (a `dark` class on `<html>`, watched by a `MutationObserver` injected via `AddScriptToExecuteOnDocumentCreatedAsync` and reported over `postMessage`), **not** from the OS: it is a per-user setting *inside* the app, so the OS preference is right only until someone overrides it — which is precisely when they are looking at the seam. Windows' setting is used once, before any page has loaded. ⚠️ Every DWM call is unchecked and allowed to fail: caption colouring is Windows 11+, the immersive-dark attribute was renumbered in Win10 20H1, and a cosmetic attribute must never be why a clinic's shell will not start. |
| `App.xaml` / `.cs` | WPF entry point, plus the shell's **palette and control templates**. The eleven `Shell*` brushes are consumed with `DynamicResource` — a `StaticResource` would bake the light value in and `WindowTheme.Apply`'s swap would silently do nothing. ⚠️ The buttons and the text box replace their `ControlTemplate` rather than setting properties: WPF's default templates paint *system* chrome and discard a `Background` on hover, so under the dark palette a bright grey rectangle appears under the cursor on a near-black panel. |
| `ArchiveCopySettings.cs` | What this machine was told about the automatic archive copy (`clinic-archive-auto-copy`) + its store, on `ServerConfigStore`'s shape (`%AppData%\ClinicManagement\archive-copy.json`). ⚠️ **Beside `server.json`, never in the archive folder** — the grant is a credential, and keeping it with the copies would mean every copy carried the key to fetch the next. ⚠️ **Absent means the feature is off, not misconfigured** (AC-10). ⚠️ `IsDue` judges from the **newest file on disk**, never a stored « last run »: a laptop closed for a week must copy on next launch rather than miss the window, and a timestamp would also disagree with the folder the moment somebody moved a file. |
| `ArchiveCopyService.cs` | The pull itself, and **the shell's first authenticated HTTP call** — everything before it was a viewer that never held a credential. Exchanges the grant for a short-lived token, streams `GET /api/backup/archive` to a `.part` file, renames only on a completed stream, then prunes. ⚠️ **No custom certificate validation, deliberately**: `HttpClient` uses the machine trust store, which is exactly where the client installer put a LAN CA and where Let's Encrypt already is — a permissive callback would cover a man-in-the-middle on the one transfer carrying the whole record. ⚠️ **Pruning runs strictly after the rename**, or a failure would trade a copy we have for one we might not get. ⚠️ `HardenFolder` re-implements `DirectoryAclHardener`'s policy (the shell references no API assembly) and is **best-effort**: a network share or exFAT stick supports no ACLs, and refusing to copy there would remove the capability over a hardening that volume could never offer. ⚠️ `IsDriveEncrypted` returns **null for « je ne sais pas »**, which is the common answer since `manage-bde` needs elevation — asserting « non chiffré » unverified would be the confident-wrong-answer class this repo keeps deleting. |
| `ArchiveCopyWindow.xaml` / `.cs` | Where that copy is set up — folder, key, cadence, retention — plus « Copier maintenant » so the setup is verifiable on the spot rather than a week later. ⚠️ **A separate window, not a sixth `MainWindow` view state**: those five are mutually-exclusive states of *reaching the server*, and this is a setting the app should stay on screen behind. ⚠️ It states in French that the folder holds the whole medical record **unencrypted** and reports the drive's BitLocker status in three states, but **never refuses** — the drive's own encryption is the right layer (AC-8). |
| `Assets/app.ico` | The window, taskbar, alt-tab and Explorer icon, embedded via `<ApplicationIcon>` and reused by **both** installers as their `SetupIconFile`. **Generated** from `web/branding/icon.svg` by `web/scripts/generate-icons.mjs` (7 sizes, 16→256) — never hand-edited, or the shell's tile drifts from the web app it renders. |
| `ClinicManagement.DesktopShell.csproj` | `WinExe`, `net8.0-windows`, `UseWPF`; single `Microsoft.Web.WebView2` package reference. No RID pinned — `dotnet build` stays framework-dependent for review; the self-contained `win-x64` publish is driven by `packaging/publish-server.ps1`. |

## Gotchas
- Runtime requires the **Microsoft Edge WebView2 Runtime** on the target PC. The **client installer** (`packaging/client/clinic-client.iss`) bundles an offline standalone installer and runs it silently **only when the runtime is missing** (S7); a still-missing runtime surfaces as the unreachable screen, not a crash.
- **The automatic copy runs once per session**, on the first successful navigation (`RunArchiveCopyIfDue`), fire-and-forget and silent on failure: it runs behind a clinic's day and a toast about a backup would interrupt a consultation for something nobody asked for. A failure is surfaced where it can be acted on (the settings window's « Copier maintenant »), and the server keeps nagging « aucune archive n'est sortie » until one lands, so a silently failing schedule cannot look healthy.
- Cannot be built/run in CI — needs Windows + the WebView2 runtime (operator-verified, R-1). It does `dotnet build` clean.
