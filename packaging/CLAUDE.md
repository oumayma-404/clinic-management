# Packaging — Local / offline-LAN Windows delivery (Phase 5)

Build recipe + **one** Inno Setup installer that turns the app into a self-contained offline-LAN Windows product. **Local mode only — Cloud is unaffected.**

⚠️ **The `.iss` NOW COMPILES IN CI** (`.github/workflows/ci.yml` § `installers`, `windows-latest` + ISCC against stub payloads). R-1 still holds for everything else: `publish-server.ps1` and the end-to-end stand-up run on an operator build machine (Windows + .NET 8 SDK + Node + Inno Setup 6) and are proven by the checklist in `README.md`, not by a CI pass. « Compiles » and « installs » are different claims and only the first one is automated.

> **Operator procedures live in `README.md`** — build prereqs, run steps, backup/restore, offline admin recovery, fresh-vs-reinstall, ports, and the per-AC verification checklist. This file is the AI map; jump to `README.md` for the how-to.

## Files
| Path | Role |
|------|------|
| `fetch-build-tools.ps1` | One-time build-machine helper — downloads PostgreSQL 16 binaries → `build-tools/pgsql/` and NSSM → `server/tools/nssm.exe`. Does **not** fetch Inno Setup (needs elevated `winget install JRSoftware.InnoSetup`). |
| `publish-server.ps1` | Build & publish orchestration. **Owns the release version**: `Resolve-Version` reads the shell `.csproj`'s `<Version>` (or `-Version x.y.z`), stamps it into the shell assembly with `/p:Version` and passes it to the `.iss` with `/DAppVersion`, so the setup filename and the version the running shell reports as `X-Client-Version` cannot disagree — they were three hand-edited literals before, and a mismatch made the server's own client floor refuse the build just shipped. Publishes the API (self-contained `win-x64`, `UseWindowsService`) + the `desktop/` shell; builds the Next.js standalone bundle with same-origin env (`NEXT_PUBLIC_API_URL=/api`, `AUTH_MODE=local`, `API_INTERNAL_URL`); stages Node + PostgreSQL `bin/lib/share` runtimes; **scrubs real-looking secrets** from the *published* `appsettings.json` (source untouched); packs the Velopack feed with `vpk` into `server/updates/`; optionally compiles the `.iss`. Stages into `build-output/` (gitignored). Third-party runtimes are not fabricated — pass `-PostgresDir` / `-NodeDir`. |
| `setup/clinic-setup.iss` | **The installer. One file, and its first page asks what this PC is** — `IsServerRole` is what every `[Dirs]`, `[Files]` and `[Icons]` entry is gated on. **Serveur**: bundled PostgreSQL 16 (fresh cluster or reuse persisted creds), API + Node web as auto-start services (dep order **DB→Web→API**), `appsettings.Production.json`, install-time cert provisioning (`provision-cert`), firewall (opens only `5001`/`5080`, removed on uninstall), CA export, **`DisableSleepOnMains`** and **`AnnounceServerAddress`**. **Poste**: carries no payload at all — it fetches the CA from `http://<host>:5080/api/trust/ca.crt`, shows the SHA-256 for a human to accept, imports it, then downloads and runs the Velopack setup from `/api/meta/client-download`. |
| ~~`server/clinic-server.iss`~~ · ~~`client/clinic-client.iss`~~ | **Merged into the above, and the client half was a defect rather than a component.** (1) It imported a `ca.crt` staged by hand from a server that does not exist at build time, with `skipifsourcedoesntexist` — so every compiled client setup imported **nothing**, silently by design (« absent is a valid state »), and every staff PC met a certificate warning. (2) The shell it installed **could never self-update**: `ShellUpdater.CheckAndStageAsync` returns `null` when `UpdateManager.IsInstalled` is false, which is exactly what an Inno install under `%ProgramFiles%` is — so « Mettre à jour maintenant » did nothing, for ever, with no error. |
| `server/tools/nssm.exe` | NSSM — hosts the Node web server as a Windows service. Operator-supplied (via `fetch-build-tools.ps1`); pulled by the `.iss` from here (not `build-output/`). Gitignored. |
| `lint-iss.mjs` | The cheap half: no Windows, seconds, fails on a `{ }` comment whose own `}` closes it early (a `{app}`-style constant, or a `[Section]` tag at line start). CI's `packaging` job. |
| `ci-stub-payloads.mjs` | What lets ISCC compile in CI: ISCC refuses a `Source:` matching no file, and the real payloads are ~450 MB. ⚠️ **It derives the list from the `.iss`**, never a hand-kept one, skips `skipifsourcedoesntexist` entries and **refuses to write outside `build-output/`** — without that last guard it wrote a 122-byte stub over `server/tools/nssm.exe`, which the next real build would have shipped as a service host. |
| `build-tools/` | Fetched build-time tools (PostgreSQL, NSSM). Gitignored. |
| `build-output/` | Staged payloads + the compiled `ClinicManagementSetup-<version>.exe`. Gitignored. |

## Flow
1. `fetch-build-tools.ps1` (once) → runtimes into `build-tools/` + `server/tools/nssm.exe`.
2. `publish-server.ps1 -PostgresDir … -NodeDir …` → stages `build-output/server/{api,web,node,postgres}` and `build-output/client/{shell,releases}`, packs the Velopack feed into `server/updates/`, then compiles the one `.iss` (unless `-SkipInstallers`).
3. **There is no step 3 any more.** It used to be « drop the server-exported `ca.crt` and the offline WebView2 installer into `build-output/client/…` » — two manual stagings that were never actually done, which is why neither ever shipped. Both are fetched at install time now.

⚠️ **`vpk` missing is a FAILURE, not a warning** (it used to be a warning). The Velopack feed's own `Setup.exe` is the only thing a workstation install can download, so a server built without one cannot set up a single staff PC.

## Key facts (verified)
- **Kestrel is the sole LAN-facing endpoint** — HTTPS `5001` open on the firewall; Node web `3000`, API HTTP `5000`, PostgreSQL `5432` are all loopback-only.
- **No real secret ships** — `publish-server.ps1` blanks Google/HuggingFace/Auth0/MinIO + the connection-string password in the published `appsettings.json`; runtime secrets self-generate into the per-install, gitignored `api/.local/` on the target. PostgreSQL passwords are CSPRNG-generated, scram-sha-256.
- **Permissions are set by the app, not the script** (security-hardening Part 1, audit § 2 findings 1–4). `[Dirs]` no longer carries `Permissions:` — Inno's flag only *adds* an ACE and leaves the inherited `Users: Read & Execute` from Program Files intact, which was the defect. Instead the `.iss` invokes three new **API console verbs** (joining `provision-cert` / `reset-admin-password`): `harden-permissions <dirs…>` (breaks inheritance, grants `LocalSystem`/`NetworkService`/`Administrators` only, removes `Users`/`Everyone` recursively), and `protect-credentials` / `read-credentials --out <file>` (encrypt / decrypt `.local/db-credentials`, machine-scoped, migrating a legacy plaintext file on upgrade). The policy therefore has **one unit-tested C# implementation** — `Infrastructure/Security/DirectoryAclHardener` — shared with the one-click backup, instead of `icacls` logic duplicated in untestable Pascal. `pgdata`'s `initdb` grant is revoked immediately after `initdb`, **including on its failure path**. Every step fails loud and aborts the install.
- **`Infrastructure/Security/LocalDataProtection` is the single Data Protection key-ring definition** — used by both `AddInfrastructure` and the console verbs. They must not drift: if the installer wrote ciphertext the API could not read, an existing cluster would be unreachable. Same convention `LocalAuthConfig` applies to the signing key.
- **Inno `{ }` comments must not contain `{app}`/`{sys}`/`{tmp}`, or a `[Section]` tag** — Pascal comments do not nest, so the first `}` (the one closing the constant) ends the comment early and the rest of the line is parsed as code. Use `//` for any comment mentioning a path constant. ⚠️ **This rule was already written here and got broken anyway, twice**, because nothing enforced it: ISCC is not CI-runnable and the `.iss` files went months without a compile, during which the server installer stopped building at all. `lint-iss.mjs` is the enforcement; a note in a map file was not.
- **CA subject is `CN=Clinic Management Local CA`** (`api/…/Security/CertificateProvisioner.cs`) — the client `.iss` `certutil -delstore Root` uninstall match depends on this exact name.
- **`provision-cert` / `reset-admin-password`** are API console commands (`api/ClinicManagement.API/Maintenance/`), invoked by the server installer / operator respectively.
