# Implementation Plan: In-App Staff Notification Center

**Status:** APPROVED
**Created:** 2026-07-14
**Spec:** [./spec.md](./spec.md)
**Type:** Full pipeline (single implementation story per planning decision)

## Overview

Deliver the clinic-scoped, per-user in-app notification feed described in the spec: a bell + unread badge in the dashboard header opening a panel of recent notifications, generated by four triggers (appointment created / cancelled / rescheduled, low stock) plus a read-time 24h reminder, with per-user read/unread state, deep-link navigation, and live updates over the existing SignalR pipeline.

Per the planning interview, this is implemented as **one vertical story (US-1)** spanning Domain → Persistence → Application → API → Frontend, with the four triggers and the reminder as sequential step-groups inside that story. The story is large (see R-1); it is organized below so it can be implemented and checkpointed group-by-group.

### Approved architecture decisions (planning interview, 2026-07-14)

| # | Decision | Choice |
|---|----------|--------|
| D1 | Data model | **New `StaffNotification` entity + `NotificationRead` join table.** One clinic-shared notification row; per-user read tracked in the join table. No write-time fan-out. |
| D2 | Generation | **Inline, best-effort, in the command handlers** (Create/Update appointment, Update stock). No global domain-event dispatch → the dormant outbound `AppointmentCreatedEventHandler` stays dormant (spec hard constraint). |
| D3 | Live signal | **The generator explicitly broadcasts the `"notifications"` realtime key** after creating notifications, regardless of source; frontend subscribes to `"notifications"`. New key added to the frontend `RealtimeResource` map + the resolver contract test, in lock-step. |
| D4 | Unread badge | **Separate lightweight `GET /api/notifications/unread-count`** for the always-on badge; the 50-row list is fetched only when the panel opens. |

### Naming note (avoid clash)

The existing `ClinicManagement.Domain.Entities.Notification` models the **outbound** email/SMS reminder and must stay untouched. The new in-app entity is therefore named **`StaffNotification`** (feature folder is still `Features/Notifications`, so the realtime key auto-derives to `"notifications"` — the key is folder-based, not entity-based).

## Implementation Story

### US-1: In-app staff notification center (full vertical slice)

**Layer:** Full (BE + FE)
**Spec coverage:** US-1 … US-6 (all).

Implement in the following step-groups, in order. Each group leaves the build green (`dotnet build` 0/0; `tsc --noEmit` + `npm run build` clean).

#### Group A — Domain + persistence (the store)
1. `NotificationCategory`, `NotificationTargetKind` enums.
2. `StaffNotification : AggregateRoot<Guid>` with private setters + a public ctor and intention-revealing methods:
   - Fields: `ClinicId (Guid)`, `Category`, `Title (string)`, `Message (string)`, `EffectiveFeedTime (DateTime UTC)` (creation time for immediate categories; due time for reminders — this is the ordering/due/baseline anchor), `ActorUserId (string?)` (user to exclude; null = visible to all), `TargetKind`, `AppointmentId (Guid?)`, `StockItemId (Guid?)`, `CreatedAt (DateTime UTC)`.
   - Reminder mutability: a `MoveReminder(DateTime newDueUtc)` method (updates `EffectiveFeedTime` + title/message) for reschedule.
3. `NotificationRead` with composite key `(NotificationId, UserId)` + `ReadAt (DateTime UTC)`.
4. EF configs (follow `StockItemConfiguration`): enums `HasConversion<int>`, `Title` max-length, `Message` as `text`, `ClinicId` FK + index, index on `(ClinicId, EffectiveFeedTime)` for the ordered/capped read path; `NotificationRead` composite key + FK to `StaffNotification` (cascade delete) + index on `UserId`.
5. DbSets + global-query-filter entries; `IStaffNotificationRepository` + impl with:
   - `GetRecentByClinicIdAsync(clinicId, take)` — ordered `EffectiveFeedTime` desc, `EffectiveFeedTime <= now`, `Take(take)`, includes read markers for the current user (or fetch read set separately).
   - `CountUnreadAsync(clinicId, userId, userCreatedAt, now)` — the aggregate.
   - `GetReadNotificationIdsAsync(clinicId, userId, notificationIds)` / read-set helper.
   - `AddAsync`, `AddReadAsync`, `GetPendingReminderByAppointmentAsync(appointmentId)` (category=Reminder, not yet due), `RemoveAsync` (for reminder suppression).
6. Migration.

#### Group B — Read side (list + count + mark-read)
7. `NotificationDto` (`id, category (string), title, message, createdAt (=EffectiveFeedTime ISO), isRead, targetKind, appointmentId?, stockItemId?`) + `ToDto`.
8. `GetNotificationsQuery` — resolve actor (`IClinicContext.GetUserId()` → `IUserRepository` for `ClinicId` + `CreatedAt`); fetch recent 50 (due, **excluding `ActorUserId == me`** — actor-excluded are hidden entirely); annotate `isRead = hasReadRow || EffectiveFeedTime < me.CreatedAt` (late-joiner baseline).
9. `GetUnreadCountQuery` — count due notifications where `ActorUserId != me`, `EffectiveFeedTime >= me.CreatedAt`, and no read row. Display cap (`99+`) is client-side.
10. `MarkNotificationReadCommand` — tenant check (`notification.ClinicId != myClinic` → `Failure("Notification not found")`); insert `NotificationRead` if absent; idempotent.
11. `MarkAllNotificationsReadCommand` — insert read markers for **all** of my currently-unread notifications (not just the 50), so the badge reaches 0.
12. `NotificationsController` with the four routes (`GET /`, `GET /unread-count`, `PUT /{id}/read`, `PUT /read-all`).
13. Update `RealtimeResourceResolverTests` for the `"notifications"` key.

#### Group C — Generation seam + first trigger (appointment created)
14. `INotificationGenerator` + `NotificationGenerator` (scoped, DI-registered). Each method is best-effort: its **own** `try/catch` that logs at Warning and swallows (narrow the swallow so a genuine programming error is still visible — per the InternetProbe learning, don't blanket-swallow into silence). It persists via the repo + `IUnitOfWork.SaveChangesAsync` **after** the caller's commit, then calls `IRealtimeNotifier.NotifyEntityChangedAsync(clinicId, "notifications")`.
15. Wire into `CreateAppointmentCommandHandler`: after the existing `SaveChangesAsync`, if `PatientId` present, generate `AppointmentCreated` with `ActorUserId = userId` (the creator, excluded), `AppointmentId`, French title/message naming patient + date/time. Patient-less busy slots generate nothing.

#### Group D — Reminder (US-4)
16. In `CreateAppointmentCommandHandler`, also schedule the 24h reminder: if patient present and `AppointmentDateTime - 24h > now`, create a `Reminder` notification with `EffectiveFeedTime = AppointmentDateTime - 24h`, `ActorUserId = null` (all staff), `AppointmentId` set. (<24h → skip; the created-notification suffices.)
17. Reminder due-ness is already enforced by the `EffectiveFeedTime <= now` filter in Group B queries — no scheduler.

#### Group E — Cancel + reschedule triggers (US-3) incl. reminder lifecycle
18. In `UpdateAppointmentCommandHandler`: inject `IClinicContext` for the actor user id; capture `oldStatus` + `oldDateTime` **before** the mutation block. After commit:
    - If the appointment became `Cancelled` (old ≠ Cancelled, new = Cancelled) and has a patient → generate `AppointmentCancelled` (actor-excluded); **suppress** any pending reminder (`GetPendingReminderByAppointmentAsync` → `RemoveAsync`).
    - Else if the date actually changed → generate `AppointmentRescheduled` (actor-excluded, naming old + new date/time); **move** the pending reminder to `newDateTime - 24h` (create one if none and >24h out; remove if now <24h out).
    - **Guard the reactivation edge:** cancelled→scheduled reactivation calls `Reschedule(sameDateTime)` (line 156). Do **not** emit "rescheduled" when `oldStatus == Cancelled` and the date is unchanged.

#### Group F — Low-stock trigger (US-5)
19. In `UpdateStockItemCommandHandler`: capture `wasLow = item.IsLowStock()` before the `UpdateInfo`/`UpdateStockLevels`/`SetCurrentStock` calls; after commit compute `isLowNow`; if `!wasLow && isLowNow` → generate `LowStock` (`ActorUserId = null`, `StockItemId`, `TargetKind.StockItem`, French message naming item + current/minimum). Create path is untouched → creation-already-low fires nothing (edge-trigger + re-arm come for free from before/after).

#### Group G — Frontend
20. `NotificationDto` type; `notifications.ts` API module.
21. `Notifications: "notifications"` in `RealtimeResource`.
22. `use-notifications` hook: fetch count on mount; fetch list lazily on panel open; `useClinicRealtime(RealtimeResource.Notifications, ...)` → refetch count (+ list if open); reconnect (`undefined`) → refetch both; expose `markRead`/`markAllRead` that optimistically update then refetch count.
23. `notification-panel.tsx`: header ("Notifications" + "Tout marquer comme lu", disabled when 0 unread); scrollable list (`max-h-[…] overflow-y-auto`, no `scroll-area` primitive exists); per-row category icon, title, message, relative time (`formatDistanceToNow(new Date(createdAt), { addSuffix: true, locale: fr })`), unread indicator; empty state "Aucune notification"; loading spinner; non-blocking error.
24. `dashboard-header.tsx`: `Popover` around the bell; real `Badge` (hidden at 0, `99+` cap); render panel; refetch list on open.
25. Deep-links: row click → `markRead(id)` + close + navigate (`/appointments?appointmentId=…&date=…` or `/stock?itemId=…`). Add the query-param handling to the two pages (graceful when the target is gone — land on the list, per Edge Cases).

**Acceptance (maps to spec):** US-1 (Group B+G), US-2 (Group C), US-3 (Group E), US-4 (Group D), US-5 (Group F), US-6 (Group B: per-user read, mark-all, baseline; Group G: navigation).

## Risk Register

| ID | Risk | Likelihood | Impact | Group | Mitigation |
|----|------|------------|--------|-------|------------|
| R-1 | **Single story is large** (>25 files across 4 backend layers + frontend) — hard to complete/review in one session. | High | Med | all | Implemented as ordered step-groups A–G, each leaving the build green; `/implement-story` can checkpoint per group via `progress.md`. |
| R-2 | **Best-effort generation runs a 2nd `SaveChanges` on the same scoped `DbContext`** after the core commit; a failure could interact with the still-tracked aggregate. | Med | Med | C | Generator wraps its persist in try/catch (never rethrows); the core aggregate is already committed, so a failed notification save cannot roll it back. Consider a fresh `IServiceScopeFactory` scope (as `UpdateAppointmentCommand` already does for Google sync) if change-tracker interference appears. |
| R-3 | **Reschedule vs reactivation false positive** — cancelled→scheduled calls `Reschedule(sameTime)`; naive "date changed" logic could emit a bogus "rescheduled". | Med | Med | E | Capture `oldStatus`+`oldDateTime`; suppress "rescheduled" when `oldStatus == Cancelled` and date unchanged (explicit guard + test). |
| R-4 | **Reminder for a reschedule/cancel not moved/suppressed** → stale reminder appears (violates US-4). | Med | High | E | `GetPendingReminderByAppointmentAsync` + Remove/Move in the cancel/reschedule branches; tests for both. |
| R-5 | **`NotificationRead` has no `ClinicId`** — global query filter can't scope it directly; a naive read-marker query could touch other clinics' rows. | Low | High | A/B | Always join reads to their `StaffNotification` (which is clinic-filtered) or scope by `UserId` (a user belongs to one clinic); tenant-isolation test pins this. |
| R-6 | **Realtime key contract drift** — `"notifications"` must exist in backend resolver output *and* frontend map or the contract test fails / clients don't refetch. | Med | Low | B/G | Add the key to `RealtimeResource` and the resolver test in the same story; the test is the guard. |
| R-7 | **Mark-read broadcasts `"notifications"` to the whole clinic** → all clients refetch though read state is per-user. | High | Low | B | Harmless (each refetches its own count/list, sees no change); accepted. Not worth suppressing the auto-broadcast. |
| R-8 | **`useSearchParams` / deep-link on non-Suspense pages** could break the build or SSR (guard `window`, per LEARNINGS). | Med | Med | G | Follow the page's existing `window.location.search` + `history.replaceState` pattern (already used for the Google-auth return) rather than introducing `useSearchParams`; guard browser globals. |
| R-9 | **Timezone/`DateTimeKind` bugs** in `EffectiveFeedTime` (24h math, due comparison) — the DbContext force-converts all `DateTime` to UTC. | Med | Med | A/D | Compute all times in UTC (`DateTime.UtcNow`); mirror `UpdateAppointmentCommand`'s `SpecifyKind`/`ToUniversalTime` handling; test the <24h boundary. |

## Breaking Changes

- **None to existing behavior.** The existing outbound `Notification` entity, `NotificationService`, `NotificationJob`, and `AppointmentCreatedEventHandler` are left untouched and remain dormant (no domain-event dispatch is wired). The new feed is additive.
- The header bell changes from a static red dot to a real (sometimes-empty) badge — a visible UI change, not a breaking one.

## Migrations

- One EF Core migration `AddStaffNotifications` creating `StaffNotifications` and `NotificationReads` tables (+ indexes). Applied automatically at API startup (`context.Database.Migrate()`). No data backfill — spec forbids back-generating historical notifications; the late-joiner baseline (`EffectiveFeedTime` vs `User.CreatedAt`) makes pre-existing rows show as read for everyone at go-live, so no historical rows exist to migrate anyway.
